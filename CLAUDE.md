## Architecture (big picture, from docs)

- **Modular monolith API** (Fastify + Zod, Drizzle ORM on Postgres 16 + pgvector). Modules (`routes/service/repo/schemas`) talk only through service interfaces, never cross-module repos. Extract services only for the judge and AI orchestrator. API is `/v1`; errors are `AppError` mapped centrally to `{ error: { code, message, details, requestId } }`.
- **Judge**: submissions are enqueued (BullMQ/Redis) and executed by judge workers using `isolate` in hardened Linux containers. Judge workers are the only code that runs untrusted code and have **no DB credentials and no network**. Progress streams via Redis pub/sub -> WebSocket gateway (docs 08 §4.1, 12, 14). `isolate` is Linux-only: on Windows run it in a privileged Docker container (WSL2).
- **Interview engine**: WebSocket gateway -> session orchestrator (state machine, stateless between turns) -> LLM gateway (single entry for all Claude calls: model routing, streaming, budgets, PII-redacted logging, schema-validated JSON with repair loop). Model names come from env config, never hard-coded. Scorecards are generated async with structured JSON that must cite evidence (docs 08, 13).
- **Pure core logic** (scoring, SRS, readiness, planner, verdicts) lives in `packages/*-core` with no I/O. Study plans are deterministic; LLM only for narrative (ADR-007).
- Server-authoritative timers/scoring/unlocks; Zod contracts shared between web, API, workers; trace IDs propagate through HTTP, queues, WS, LLM calls.

## Code conventions

- Auth model: access JWT held in memory only; refresh token is an httpOnly rotating cookie (`pq_rt`, Path `/v1/auth`); the web client shares a single in-flight refresh (a parallel second use looks like token theft and revokes the family). Protect API routes with `preHandler: app.authenticate` (or `app.requireRole(...)`) and read the caller from `req.auth`. Validate every body with `parse(zodSchema, body)` (`src/lib/validate.ts`); schemas shared with the web live in `packages/shared`.
- DB: edit `packages/db/src/schema`, run `pnpm db:generate`, review and commit the SQL (never edit an applied migration). Every table needs `created_at`/`updated_at` and **its own `updated_at` trigger in its migration** (a test enforces both). Repositories are plain functions taking a `Db` (database or transaction) built on the Drizzle query builder; Zod schemas in `packages/shared` use the same property names as the schema so updates need no mapping. Extensions and triggers are custom SQL migrations (`drizzle-kit generate --custom`).
- Rate limiting: global per-user/per-IP budget is in `app.ts`; per-email/per-user limits use `ctx.limiter`, wrong-code budgets use `AttemptGuard`, login uses `LoginLockout`. All fail open if Redis is down. Routes with their own `config.rateLimit` get a separate bucket from the global one. Gate costly features with `preHandler: app.requireVerifiedEmail`; privileged roles need `mfa` on the token (`app.requireRole`).
- Secrets: never log or return password hashes, token hashes or TOTP seeds (seeds are AES-GCM encrypted with `DATA_ENCRYPTION_KEY`). OAuth sign-in must go through `resolveAccount` so the pre-hijack linking rules apply.
- `@fastify/cors` methods and exposed headers are listed explicitly in `app.ts`; a new verb or a header the browser must read needs adding there. Playwright: each test gets a fresh page (sign in again), locators for error text must not use `role=alert` (Next.js route announcer has it), and TOTP codes for the previous step must be computed away from a 30 s boundary.
- TS `strict` (+ `noUncheckedIndexedAccess`), no uncommented `any` (lint-enforced), `consistent-type-imports`; kebab-case files, PascalCase components, plural snake_case tables, UUID v7 PKs, forward-only migrations (expand/contract for destructive changes). Mailpit (dev inbox) at http://localhost:8025; e2e reads emails from its API.
- Frontend: all colors/fonts via design tokens (doc 07), never hard-coded hex; feature folders; no business logic in components; `jsx-a11y` on. Use `@prepquest/ui` components; for a link that looks like a button use `buttonClasses()` (never wrap a button in a link). Pixel look: `.pq-box` (notched outline via box-shadows) + `.pq-lift` (hard `drop-shadow`), see doc 07 §13. Tailwind v4 is CSS-first in `apps/web/src/app/globals.css`. Pixel fonts for chrome only; long text uses the read font.
- Verify UI visually: `pnpm build && npx next start` in `apps/web`, then headless Chrome `--screenshot` of `/design` (Chrome is at `C:\Program Files\Google\Chrome\Application\chrome.exe`).
- API: cursor pagination, idempotency keys on expensive POSTs, OpenAPI from Zod.
- Conventional Commits, trunk-based, squash merge. Never commit `.env` or `secrets/`.
- Use TypeScript `~5.9` (typescript-eslint doesn't support TS 7). `docs/` and `CLAUDE.md` are prettier-ignored.
- Content: `content/problems/<slug>/` is the source of truth (see docs 17 §11); changing a problem's content creates a new version (hash), old versions keep their tests. Test I/O follows the codec in doc 12 (`packages/content/src/codec.ts` + `python/harness.py`); judge drivers must match it. Admin roles: editors touch only their own drafts, reviewers/admins publish/archive, every write is audited.
- Drizzle gotcha: in single-table select-list subqueries `${table.col}` loses its table prefix; use raw qualified names. `TRUNCATE users CASCADE` also wipes problems in tests (import fixtures after `makeTestApp`).
- Monaco: the editor owns its text while typing (never drive it with a controlled `value`); colors must be 6/8-digit hex (`editor-colors.ts`); a textarea fallback shows if the CDN load fails.
- Judge protocol: API inserts the submission and enqueues a BullMQ job that carries everything (source, signature, checker, limits, test keys); the worker publishes events to the Redis stream `judge:results`; the API's `ResultIngester` is the only writer to the database and applies events idempotently (`applyJudgeEvent`). Hidden test data never reaches the browser (the worker omits it and `getSubmission` filters again). The worker must never receive database, JWT or SMTP settings (`apps/judge/src/config.ts`). A new parameter type needs the codec (`packages/content`), the Python harness and all three drivers (`packages/judge-core/src/drivers.ts`) changed together; the driver tests cover it.
- Under isolate commands must be absolute paths (it doesn't search PATH, `/etc` is invisible); see `defaultCommands()`. Don't run submitted code with `ProcessSandbox` on shared hosts.
- Web judge UI: send and poll in `features/submissions/use-judge.ts`; verdict display in `@prepquest/ui` `VerdictBanner`. In Playwright put code into drafts through the API (`saveDraft`), because typing into Monaco auto-indents.
- Never commit `__pycache__` (ignored): reference solutions are imported by Python tools.
- Progress rules live in `packages/analytics-core` and are applied by the API only: XP, level, streak, activity and badges are awarded in `modules/progress/award.ts` inside the judge-result transaction (`submissions/ingest.ts`); hint and editorial unlocks in `modules/practice` (the web only displays them). Never compute XP or unlocks in the browser. `user_problem_state.first_seen_at` starts the cooldowns (set when a signed-in user opens a problem).
- Hints and editorials are not versioned: the content hash must ignore them. Content per problem: `hints/{1,2,3}.md`, `editorial.json` (code may be `{ "file": "solutions/ref.py" }`), `solutions/mutants/*.py` with a `# expect: <VERDICT>` header; `pnpm content:judge` must stay green when tests or solutions change.
- A VS Code extension (Console Ninja) can patch `node_modules/next`; if `next start` says "startServer is not a function", reinstall Next (and don't leave a shell cwd inside `node_modules`).
- Interviews (Phase 6): the model talks, code decides. Every rule lives in `packages/interview-core` and is applied in `modules/interviews/engine.ts`: state transitions (`decideNext`; the model's `next_state` is only a proposal and can never end a session), hint budget and ladder (`validateControl`, regenerate once), solution-leak check, 85% wrap-up, timer. All model calls go through `LlmGateway` (`apps/api/src/lib/llm`); model names are env config and no `temperature` is sent (the five-series models reject it). Candidate, resume and JD text is untrusted: sanitize with `sanitizeCandidateText`/`neutralizeTags` and keep it in delimited blocks. The scorecard overall is computed in code from the rubric weights; scores need evidence whose quotes are verified against the transcript; correctness comes from the judge's submission rows (`interview_session_id`), never from the browser. Hints and editorials are `HINT_LOCKED` while a problem is in the user's live interview (`modules/interviews/access.ts`). Streaming uses `interviewer.token` and `interviewer.retract`; the web room state is the pure reducer in `features/interview/room-state.ts`. Register socket handlers before any `await` in the connection handler. Background jobs (`BackgroundRunner`) persist their own status; tests `await t.idle()`. Tests: `t.mock` (scripted provider with `overrides`), `t.app.ai.now` to move the clock, `t.app.interviews.sweep()` for the timer; `makeTestApp` truncates users, so give rate-limit tests their own file.
- Voice and reactions (Phase 7): proactive interviewer messages are rules first (`interview-core/reactions.ts`: cooldown, typing quiet time, caps, interruption level) and a light-model classifier second; they are processed by the timer sweep from `state_data.pendingReaction`. Speech runs in the browser (`features/interview/voice`): the pure helpers in `speech.ts` are unit tested, `use-voice.ts` wires Web Speech, and only final interviewer replies are spoken because the leak and hint checks need the whole reply. Chrome defines `SpeechRecognition` and `webkitSpeechRecognition`: fakes must define both. Voice sessions need `FF_VOICE`. `pnpm eval:ai` must stay green (hard gates) when prompts, guards or the control channel change; run it with `--live` and a key before trusting a prompt change.
- Interview types, packs, extras and memory (Phase 8): a new type is a template in `interview-core/templates.ts` plus a rubric, a `TYPE_GUIDE` entry in `packages/prompts` and mock lead text; the question comes from the bank (`source: "bank"`, kind `verbal`), problems or the resume. Packs are data (`content/company-packs/*.json`), never hard-coded; unverified inferred packs are flagged and private. Rubric weights from a pack are applied in `scorecard.ts` with `withWeights`, never trusted from the model. Review extras (`modules/interviews/extras.ts`) run after the scorecard and fail without blocking it; STAR rewrites go through `inventedFacts`. Speech numbers are code, not model output. The API consumes `@prepquest/content` and `@prepquest/shared` from `dist/`: rebuild them after changing exports. `pnpm content:validate` must stay green when the bank or packs change.
- Analytics and planning (Phase 9): scoring and scheduling rules live in `packages/analytics-core` (`readiness.ts`, `plan.ts`, `goals.ts`, `trends.ts`, `timing.ts`) and are pure; the API only loads a `Learner` snapshot (`modules/analytics/learner.ts`) and persists results. The planner is deterministic and the language model never schedules. Readiness must not call a thin-evidence learner ready (evidence is pulled towards a prior); keep the band honest and say "not enough data" rather than guessing. A plan task is identified across re-plans by its `key`; never edit a task's key, and keep missed tasks as `moved` history. Plan settings precedence is request, saved plan, profile. Goal XP is paid by an atomic claim on `daily_goals.rewarded`. Use `z.partialRecord` for optional-key records. Tests for "today" that depend on `first_ac_at` must use the real clock; plan tests can pin `t.app.ai.now`. `test/solve.ts` has `solveProblem` and `resetLearning`.
- Learning suite (Phase 10): rules live in `packages/analytics-core` (`srs.ts`, `quiz.ts`, `roadmap.ts`, `tracks.ts`) and are pure; the API modules `reviews`, `quizzes`, `roadmaps` and `tracks` only load and store. A card is created and auto-reviewed inside the judge-result transaction (`submissions/ingest.ts` calls `reviews/service.ts afterAccepted`, practice mode only); due dates are the learner's local `date`s. Quiz answers are graded and the key is held on the server (`gradeAnswer`); timed tests end on the server clock (`deadline_at`); XP is paid once, on first finish, only for questions never answered correctly before. Quizzes and roadmaps are content (`content/quizzes/<subject>.json`, `content/roadmaps/<slug>.json`): `pnpm content:validate` must stay green, and a roadmap node needs a topic, a quiz subject or a problem ladder. A company track is a published, non-provisional pack. `content:import` upserts quizzes and roadmaps by slug. Tests that tie on timestamps need the `created_at` tie-break; `test/content.ts` has `seedLearning`.
- Assessments (Phase 11): learner SQL goes through `guardQuery` (`analytics-core/sql.ts`) and then `runQuery` (`packages/sql-runner`), which builds a fresh in-memory database per run; never run SQL any other way, and never add a persistent or shared database for it. The expected result is computed by running the problem's `expected` query, so `pnpm content:validate` (which runs them for real) must stay green. OA rules live in `analytics-core/oa.ts` (pure): the API stores the attempt state, `syncClock` closes expired sections lazily on read and write, a finished section is locked, and the answer key only appears in the report. Responses travel as strings and are parsed per type before grading. XP for SQL and tests is paid through `modules/progress/xp.ts`. Content: `content/sql/<dataset>.json` (schema, seed, problems), `content/aptitude/<section>.json`, `content/oa/templates.json`; `content:import` upserts all of it by slug. The sql-runner package must be built (`pnpm build`) before the API or content CLI import it.
- Contests (Phase 12): scoring and ranking live in `analytics-core/contest.ts` (pure, scenario-tested); the API computes standings from `submissions` with `mode = 'contest'` on every request (no ZSET, no stored standings table). A contest attempt is accepted only inside the learner's own window: a live participation follows the contest's `starts_at` and `ends_at`, a virtual one has its own clock (`contest_participants`). Hints and editorials for contest problems are refused with `HINT_LOCKED` while the window is open (`modules/contests/service.ts assertNoContestLock`, used by `practice/routes.ts`). Private contests are invisible without the invite code, registration or authorship. Public contests need a reviewer or admin. Contest tests use the real clock (submission timestamps are written by the database) and move windows with SQL.
- Flashcards and sharing (Phase 13): card rules live in `analytics-core/flashcards.ts` (pure); every review, online or offline, goes through `POST /flashcards/sync`, which stores each `clientId` once and applies reviews oldest first (a review not newer than the card's `last_reviewed_at` is kept as history only). The web queue is `features/flashcards/offline.ts` (injected storage, unit tested; `localStorage`, no service worker yet). Starter decks are content (`content/flashcards/<slug>.json`, upserted by slug as ownerless decks with a `starter_slug`); learners copy them. A shared report (`modules/shares`) stores a filtered snapshot (`report.ts`, pure: scrub company and name, always redact emails, links and phones, quotes only when allowed) and only the SHA-256 of a random token; public routes `/v1/r/:token` and `og.png` answer 404 for revoked, expired and unknown links alike and are `no-store`. The preview image is drawn by `shares/og-image.ts` (own PNG encoder and 5x7 font). A test that holds a share token must not delete its owner.
- Code review and complexity (Phase 14): the model writes review comments and code checks them (`codereview/review.ts reviewIssues`: lines inside the file, severity allowed for the strictness, caps); a suggested refactor is only ever sent to the browser after the judge accepted it as a mode `review` submit. Judge runs the learner did not type (refactor checks, growth measurements) use `createReviewRun`, are stored with `mode = 'review'`, and `ingest.ts` skips progress, XP and statistics for them; the history list hides them. Growth fitting is pure (`analytics-core/complexity.ts`): log-log slope of time above the fixed cost, plausible classes within the fit error, censored (time-limit) points kept out of the fit, always labelled an estimate. Inputs come from `content/problems/<slug>/scale.json` (`analytics-core/scale.ts`, validated by `content:validate`, stored in `problems.scale`, outside the version hash). `JudgeTest.repeat` times a custom input several times and keeps the fastest. A new LLM task (`code_review`) needs a mock branch in `lib/llm/mock.ts`.
- Integrity (Phase 15): detection is pure (`analytics-core/integrity.ts`: normalised-token winnowing, trivial-program guard, starter-code hashes ignored, behaviour thresholds) and produces `integrity_flags` with evidence; it never penalises. A person decides in `/integrity` (`modules/integrity`, roles moderator, reviewer, admin; an escalated flag only an admin); only a confirmed flag sets `contest_participants.disqualified_at`, which the standings honour, and every decision is audited with its reason. Learners see only the outcome and the reviewer's reason (never the evidence or the other learner) and can appeal once. Scans are manual (`POST /admin/integrity/scan`) and repeatable (reviewed flags are left alone). Tests that need an admin or moderator mint a two-factor token with `t.keys` and `signAccessToken`.
- System design (Phase 16): the canvas model, editing operations, undo history, graph conversion, automatic design checks and the capacity calculator are pure in `analytics-core/design.ts`; the web editor (`components/design/CanvasEditor.tsx`) only renders and forwards edits, and `features/design/use-design.ts` owns history and autosave (every save carries the version it started from; a stale one is `VERSION_CONFLICT`). The model's review is checked in code (cited component ids must exist, five questions) and records the canvas version it read. Reference layers (`content/design/<slug>.json`, validated by `content:validate`: each v3 must pass `analyzeDesign` with nothing important) are served only after the learner has a reviewed attempt. The page route is `/system-design` (`/design` is the UI showcase); API routes are under `/design`. `DESIGN_NODE_TYPES` in shared must equal `NODE_TYPES` in analytics-core (tested). A new LLM task (`design_review`) has a mock branch in `lib/llm/mock.ts`.
- Design interviews (Phase 17): a round with `usesCanvas` (only `hld`) has a drawing board next to the chat. The browser sends `kind: "canvas"` events to `POST /interviews/:id/events`; the API validates the canvas, keeps the last one in `state_data.lastCanvas`, logs `canvas_snapshot` events, and gives the interviewer a `<design>` block built by `modules/interviews/design-board.ts` (components, arrows, automatic checks). `design` is a forgeable tag in `neutralizeTags`. The scorecard can cite the drawing with evidence `{type: "code", ref: "design"}`, verified against the same text. The interview drawing is not stored in `design_canvases`.
- Peer mocks (Phase 18): rules are pure in `analytics-core/peer.ts` (matching, the two halves, reputation, feedback nudges, the calendar file) and the API module `peer` only loads and stores. A match books the session at once and uses both windows up in one transaction (a lost race is a retry, never a double booking); an invite token is random and only its hash is stored, and unknown, revoked, used and expired links are the same 404. Questions stay hidden until the session is live; the current half's candidate never receives the interviewer panel (the API builds it only for the interviewer). Reputation is computed on read and judges nobody before three booked sessions; a no-show is reported from inside the room 15 minutes after the start and counts only against the person who never opened it. Blocks cancel unstarted sessions and exclude people from matches and invites. AI consent is per person and `consent.both` is the only thing an analysis may read. Tests move the clock with `setClock` and clear the key-value store between cases (the match limit is per day).
